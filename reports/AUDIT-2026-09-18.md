# Senior-SEO audit of the monitoring loop — 2026-09-18

A human-directed review of the three-tier system itself (not of the listing page). Scope: are the
tiers gathering the right evidence, prioritising correctly, and spending effort where the ranking
actually moves?

**Headline verdict: the machine is sound; the strategy it is executing has a hole in the middle.**
The evidence contract, the status gate, the ownership rules and the carry-threshold discipline are
better than most commercial SEO retainers. But the system correctly identified inbound links as the
#1 lever, then (a) never measured it, (b) prescribed two placements that carry no SEO value, and
(c) let three already-answered items sit in the queue for weeks because Tier 3's findings have no
route back into state.

---

## 1. Findings

### 1.1 The #1 lever is asserted, never measured — **fixed today**

`state/last-snapshot.json → inbound_links.external_links_known: 0` carries the note "Restate every
week until evidence shows links exist." No mechanism in any tier could ever produce that evidence.
Tier 1 has no backlink source; the number was hard-coded at scaffold time and copied forward.

Fix applied: `state/competitors.json → mention_query` — a literal `"eastlakeview503.relahq.com"`
search every Tier 1 run, with the monitoring repo itself excluded as a known self-mention. Plus
`owner_monthly_ask` — the GSC → Links → Top linking sites reading, which is the authoritative
number and takes the owner under a minute.

Ground truth recorded today: a literal search for the domain string returns **one** result on the
entire web — `github.com/GroovySoo/seo-eastlakeview503-watch`, this repo. Zero third-party mentions.

### 1.2 Both prescribed link placements are SEO-worthless — **fixed today**

For two weeks the top-priority action was *"Put TWO links on the internet pointing at the page:*
*(a) email signature, (b) LinkedIn Featured."*

- An **email signature** is not a page on the web. No crawler ever sees it. Its SEO value is exactly
  zero. Calling it one of "two links on the internet" is a category error.
- **LinkedIn Featured** links are `rel="nofollow"`, rendered client-side, and routinely uncrawled.
  Near-zero ranking value.

So the single highest-priority item in the system would not have moved rankings even if the owner
had complied perfectly. Both are fine referral-traffic habits and both are now recorded under
`link_targets.explicitly_not_link_targets` so they cannot be re-prescribed as links.

### 1.3 The best available link was never asked for — **fixed today**

`https://omar-senghore.cbdanforth.com/` — the owner's own Coldwell Banker Danforth bio page —
returns HTTP 200, carries a **"Featured Listing"** section, and mentions `1550 Eastlake` and
`eastlakeview503` **zero times** (verified 2026-09-18). Owner-controlled, free, topically perfect,
on a real-estate brand domain, almost certainly followed.

`state/competitors.json → link_targets` now carries five named, verified-live targets ranked by
realistic value, and `ACTION-QUEUE.md` carries paste-ready outreach text for the two that need an
email. The system previously offered generic advice; three weeks of generic advice produced nothing.

### 1.4 Tier 3's findings are stranded — structural, **flagged for a prompt change**

The README's rule is deliberate and mostly right: *"An item leaves the queue only when Tier 1
observes the change on the live page."* The gap is that **some facts Tier 3 learns can never be
observed on the page**, so they vanish:

| Fact Tier 3 learned | When | Consequence |
|---|---|---|
| GSC: "URL is on Google", Indexed = 1, Not indexed = 0 | 2026-09-16 | Still listed as an open Do-now item two weeks later |
| Rela's photo editor has **no alt-text field at all** | 2026-09-18 | Still listed as an open Do-now item |
| Owner supplied phone / brokerage / bio URL | 2026-09-16 | Item still marked "blocked, cut if not supplied by 09-21" |

Three of the queue's items were factually wrong on the day this audit started. The fix is a Tier 2
prompt change (see §3.2): Tier 2 must read every `reports/IMPLEMENTATION-*.md` newer than its own
last run and fold those findings in — while keeping the existing rule that *live-page changes* are
certified only by Tier 1. Tier 3 still never writes the queue.

### 1.5 The repo is public and outranks the listing for its own brand token — **owner decision**

A search for `eastlakeview503` returns this monitoring repository above the listing. The repo is
public and contains the owner's phone number, email address, full SEO strategy, competitor
assessments, the name-spelling problem, and the GSC verification token. Nothing here is a
credential (`.auth/` is correctly gitignored and untracked — verified), and the phone/email are on
the public listing anyway. But a public repo that ranks for the brand token, in front of the asset
it exists to promote, is an own goal. **Recommend making the repo private.** Not done here — it is
the owner's call.

### 1.6 Two spellings of the agent's name are now live simultaneously — **new, in the queue**

Verified on the live page today: `Omar Senghor` ×2 (Rela's native `Apartment.provider.name` and the
"Presented By" widget) and `Omar Senghore` ×1 (the `RealEstateAgent` node added 2026-09-18). The
brokerage bio page says *Senghore*. Splitting the agent entity across two spellings in one page's
structured data undercuts exactly the agent↔brokerage↔listing association the new node was added to
create. A 30-second owner answer unblocks it.

### 1.8 What is genuinely good and should not be touched

- The **evidence status gate** (`complete` / `partial` / `failed`) and the rule that a failed run must
  not overwrite the baseline. This was added after a real near-miss on 2026-09-11 and it is the
  single best piece of design in the system.
- **Tier 1 records facts, Tier 2 decides.** The separation held for three runs with no leakage.
- The **`indexed: no` → `inconclusive` retraction** on 2026-09-14. Tier 2 noticed its own tooling was
  lying rather than reporting a phantom problem. That is the behaviour you pay for.
- The **carry-threshold rule** (3 weeks → rewrite smaller or cut). It works; it just needs accurate
  inputs, which §1.4 now supplies.
- The **lifecycle design** — `listing_status` every run, wind-down recommended on pending/sold. A
  monitoring system that knows how to end is rare.

## 2. Cadence and cost

Three runs, zero live-page changes, and all reachable on-page work now finished. The system is a
link-acquisition waiting game.

| Tier | Now | Verdict |
|---|---|---|
| 1 — evidence | Sonnet, weekly | **Keep as-is.** It is the regression and lifecycle sentinel. A price change or a move to Pending is genuinely time-sensitive and Sonnet weekly is cheap. Its scope shrinks under §3.1 (fewer fetches, one fewer query, no PageSpeed) so it gets cheaper without losing coverage. |
| 2 — strategist | Opus, weekly | **Keep Opus; add a no-change fast path.** The judgement calls listed in §1.8 are why Opus is here. The waste is not the model, it is the output: three ~220-line memos to say "nothing changed, still zero links." Recommended rule in §3.2 — if the diff is empty and no new IMPLEMENTATION file exists, write ≤15 lines and post one Slack line. That is where ~80% of Tier 2's tokens go. |
| 3 — implementer | Opus, weekly | **Keep Opus while it exists** — it edits live structured data under an allowlist, which is exactly where the stronger model earns its keep, and a no-op run is nearly free. But see §4.1: its useful life is about one more edit. |

Downgrading Tier 2 to Sonnet would save less than the fast path and would put the §1.8 judgement
calls at risk. Not recommended.

than full rewrites, because the current prompts could not be read and should not be guessed at.

## 4. Recommendations deliberately NOT implemented

### 4.1 Retire the Tier 3 **cloud routine** after `containedInPlace` ships — **owner decision**

The allowlist is correctly scoped and genuinely safe. The problem is arithmetic: it has exactly
**one** job left. Every other open on-page item is either Rela-template-side (H1, `twitter:card`,
`og:url`, `og:locale`, `numberOfBedrooms`, lazy-loading, sitemap, robots, llms.txt, photo alt) or
owner-identity-side (links, name spelling) — none of which Tier 3 may touch, and rightly so.

Against that: a headless-browser cloud routine firing weekly, and a **monthly human chore** —
re-doing the interactive Rela login, re-exporting `.auth/rela-storage-state.json`, and re-pasting it
into `RELA_STORAGE_STATE_JSON` (first expiry: **2026-10-11**). That is a recurring cost for a
routine that will have nothing left to do.

Recommendation: ship `containedInPlace`, then **disable the Tier 3 cloud routine** and keep Tier 3
as an interactive on-demand procedure (it already works that way — both implementation reports so
far were produced interactively). This also retires the cookie-refresh chore entirely. Not done
here: the owner built this today and it is their call.

### 4.2 Do **not** widen the Tier 3 allowlist — agreeing with the owner's scoping

The audit brief invited an argument for widening. There isn't one. The natural expansion targets
(Property Description, SEO & Social) were rewritten on 2026-09-10 and are **already correct** —
title, meta description, OG and Twitter copy all carry "Riva Condos"/"Riva Condominium", the exact
address, the MLS number and the price. There is no upside there, only the chance of an unattended
agent regressing good copy. The narrow allowlist is the right call and should stay.

### 4.3 Make the repository private — **owner decision** (see §1.5)

### 4.4 Slack output — unchanged

Nothing about what gets posted to `#all-seo-eastlake` was altered. The no-change fast path in §3.2
would shorten the weekly post to one line; that is a material change to what the owner sees, so it
is written as a prompt patch for the owner to apply, not shipped silently.
